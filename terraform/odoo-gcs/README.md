# Odoo GCS Terraform Module

A self-contained Terraform module that provisions Google Cloud Platform (GCP) infrastructure for [Odoo 19.0](https://www.odoo.com/) to store file attachments externally in Google Cloud Storage (GCS), replacing or augmenting the default filesystem-based attachment storage.

## Overview

This module creates the following GCP resources:

| Resource | Terraform Type | Purpose |
|---|---|---|
| **GCS Bucket** | `google_storage_bucket` | Stores Odoo file attachments with versioning enabled, uniform bucket-level access, and deletion protection (`force_destroy = false`) |
| **Service Account** | `google_service_account` | Dedicated identity for Odoo to authenticate against GCP APIs |
| **Service Account Key** | `google_service_account_key` | JSON private key enabling programmatic access from the Odoo application |
| **IAM Binding** | `google_storage_bucket_iam_member` | Grants `roles/storage.objectAdmin` on the bucket to the service account, following the principle of least privilege |

## Prerequisites

Before using this module, ensure the following requirements are met:

1. **Google Cloud SDK** — Install the [Google Cloud SDK](https://cloud.google.com/sdk/docs/install) and authenticate with Application Default Credentials:

   ```bash
   gcloud auth application-default login
   ```

2. **GCP Project** — A GCP project with billing enabled. You will need the project ID to pass as an input variable.

3. **Cloud Storage API** — Enable the Cloud Storage API on your project:

   ```bash
   gcloud services enable storage.googleapis.com
   ```

4. **IAM API** — Enable the Identity and Access Management API on your project:

   ```bash
   gcloud services enable iam.googleapis.com
   ```

5. **Terraform CLI** — Install [Terraform](https://developer.hashicorp.com/terraform/install) version >= 1.0 (recommended).

## Usage

Navigate to the module directory and run the standard Terraform workflow:

```bash
# 1. Change to the module directory
cd terraform/odoo-gcs

# 2. Initialize the module and download the Google provider
terraform init

# 3. Preview the infrastructure changes
terraform plan -var="project=YOUR_GCP_PROJECT_ID"

# 4. Apply the infrastructure changes
terraform apply -var="project=YOUR_GCP_PROJECT_ID"
```

> **Note:** The `project` variable is **required** and has no default value. You must supply your GCP project ID via the `-var` flag, a `*.tfvars` file, or the `TF_VAR_project` environment variable. All other variables have sensible defaults specified in `terraform.tfvars`.

To destroy the provisioned infrastructure:

```bash
terraform destroy -var="project=YOUR_GCP_PROJECT_ID"
```

> **Warning:** The GCS bucket is created with `force_destroy = false`. You must manually empty the bucket before Terraform can destroy it. This is a safety measure to prevent accidental deletion of Odoo file attachments.

## Input Variables

| Variable | Type | Default | Required | Description |
|---|---|---|---|---|
| `project` | `string` | — | **Yes** | GCP project ID where resources will be created |
| `region` | `string` | `us-central1` | No | GCP region for the storage bucket |
| `bucket_name` | `string` | `odoo-attachments` | No | Name of the GCS bucket for Odoo attachments |
| `service_account_id` | `string` | `odoo-gcs` | No | Account ID for the dedicated GCP service account |
| `credentials_file` | `string` | `null` | No | Path to a GCP credentials JSON file; defaults to `null` to use Application Default Credentials (ADC) |

### Overriding Defaults

You can override any variable by passing `-var` flags, editing `terraform.tfvars`, or setting `TF_VAR_<name>` environment variables:

```bash
# Override via -var flag
terraform apply \
  -var="project=my-gcp-project" \
  -var="region=europe-west1" \
  -var="bucket_name=my-odoo-attachments"

# Override via environment variable
export TF_VAR_project="my-gcp-project"
terraform apply
```

## Outputs

| Output | Description | Sensitive |
|---|---|---|
| `bucket_name` | Name of the created GCS bucket | No |
| `service_account_email` | Email address of the created service account | No |
| `service_account_key` | Base64-encoded JSON key for the service account | **Yes** |
| `project` | GCP project ID used for resource provisioning | No |

## Extracting the Service Account Key

The `service_account_key` output contains the base64-encoded JSON private key generated by the `google_service_account_key` resource. To decode and save it to a file:

```bash
terraform output -raw service_account_key | base64 --decode > sa-key.json
```

You can verify the decoded key is valid JSON:

```bash
cat sa-key.json | python3 -m json.tool
```

> **Security Warning:** The service account key grants full object-level access (`roles/storage.objectAdmin`) to the GCS bucket. Handle it with the same care as a password:
>
> - **Never** commit the decoded key (`sa-key.json`) to version control.
> - Store the key securely using [GCP Secret Manager](https://cloud.google.com/secret-manager), [HashiCorp Vault](https://www.vaultproject.io/), or an equivalent secrets management solution.
> - Rotate the key periodically and revoke compromised keys immediately via the GCP Console or `gcloud iam service-accounts keys delete`.

## Odoo Connection

After provisioning the infrastructure, configure Odoo to use the GCS bucket for attachment storage.

### Option 1: Configure via Odoo Settings UI (`cloud_storage_google` addon)

The GCS bucket name and service account key are used to configure Odoo's `cloud_storage_google` addon:

1. Install and enable the `cloud_storage_google` addon in your Odoo instance.

2. Set the `cloud_storage_google_bucket_name` system parameter to the bucket name output:

   ```bash
   # Retrieve the bucket name
   terraform output bucket_name
   ```

3. Set the `cloud_storage_google_account_info` system parameter to the decoded service account key JSON (the full contents of `sa-key.json`).

4. Navigate to **Settings → Technical → System Parameters** in the Odoo admin interface and verify both parameters are configured correctly.

### Option 2: Configure via `debian/odoo.conf` (Deployment Templates)

For automated deployments, configure the attachment location in the Odoo server configuration file:

```ini
[options]
ir_attachment_location = gs://odoo-attachments
```

This module's deployment updates `debian/odoo.conf` with placeholder settings for GCS integration:

- `ir_attachment_location` — Set to `gs://odoo-attachments` to direct Odoo's attachment storage to the GCS bucket.
- `google_drive_client_id` — Placeholder for the OAuth client ID (override in production).
- `google_drive_client_secret` — Placeholder for the OAuth client secret (override in production).
- `google_drive_token` — Placeholder for the OAuth token (override in production).

> **Note:** The placeholder values in `debian/odoo.conf` are intended for deployment templates only. In production, override these settings via environment variables or GCP Secret Manager.

## Resources Created

This module provisions the following four GCP resources:

### `google_storage_bucket` — Odoo Attachments Bucket

- **Name:** Configurable via `var.bucket_name` (default: `odoo-attachments`)
- **Location:** Configurable via `var.region` (default: `us-central1`)
- **Versioning:** Enabled — protects against accidental object deletions or overwrites
- **Uniform Bucket-Level Access:** Enabled — enforces IAM-based access control instead of per-object ACLs
- **Force Destroy:** Disabled (`false`) — prevents Terraform from destroying a bucket that still contains objects

### `google_service_account` — Odoo Service Account

- **Account ID:** Configurable via `var.service_account_id` (default: `odoo-gcs`)
- **Display Name:** `Odoo GCS Service Account`
- **Purpose:** Provides a dedicated identity for the Odoo application to authenticate with GCP, isolated from other services

### `google_service_account_key` — Programmatic Access Key

- **Type:** JSON private key
- **Linked To:** The `odoo-gcs` service account
- **Output:** Exposed as the `service_account_key` output (base64-encoded, marked sensitive)
- **Usage:** Decoded and injected into Odoo's configuration for GCS authentication

### `google_storage_bucket_iam_member` — Bucket Access Binding

- **Role:** `roles/storage.objectAdmin` — grants permissions to create, read, update, and delete objects in the bucket
- **Member:** The provisioned service account (`serviceAccount:<email>`)
- **Scope:** Restricted to the specific GCS bucket only — does not grant project-wide storage access

## Security Notes

- **Sensitive Output:** The `service_account_key` output is marked `sensitive = true` in Terraform. This prevents the private key from being displayed in `terraform plan`, `terraform apply`, or CI/CD log output.

- **No Key in Version Control:** Never commit the decoded service account key (`sa-key.json`) or any file containing the raw key material to version control. Add `sa-key.json` to your `.gitignore`.

- **Production Authentication:** In production environments, prefer [GCP Workload Identity Federation](https://cloud.google.com/iam/docs/workload-identity-federation) or [GCP Secret Manager](https://cloud.google.com/secret-manager) over static service account keys. Static keys are suitable for development and initial setup but carry risk if leaked or not rotated.

- **Bucket Deletion Protection:** The `force_destroy = false` setting on the GCS bucket prevents Terraform from destroying a bucket that contains objects. This safeguards Odoo file attachments against accidental infrastructure teardown.

- **Least Privilege:** The IAM binding grants `roles/storage.objectAdmin` scoped to the specific bucket only. The service account has no other project-level permissions, following the principle of least privilege.

- **Key Rotation:** Periodically rotate the service account key using:

  ```bash
  # Delete the old key and re-apply to generate a new one
  terraform taint google_service_account_key.odoo_gcs_key
  terraform apply -var="project=YOUR_GCP_PROJECT_ID"
  ```

  Update the Odoo configuration with the new decoded key after rotation.
